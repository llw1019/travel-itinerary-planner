# HTML 行程手冊規格

最終產出是**一份完整的 HTML 旅遊手冊**,不是聊天室裡的條列文字,也不只是一張行程表。

這份檔案規定「要有哪些區塊與欄位」。欄位填滿之後**還要有編輯判斷**才會像手冊——那部分見 `references/editorial-standards.md`,兩份要一起用。

## 產出的文件只有兩份,不要一次做兩份

**階段一:詳細版(查閱用)** —— 這是預設產出,也是絕大多數情況下唯一要做的東西。內容密集、以文字與表格承載全部資訊,螢幕與手機上查閱為主,附基本的 `@media print` 樣式讓它印得出來。

**階段二:列印版(裝訂用)** —— **只在使用者確認詳細版的內容通過之後才做**,而且要使用者明確要求。這一版是為紙本重新編排的:一個項目一頁、頁碼、頁眉頁腳、適合裝訂的版面。

**「階段」指的是要維護幾份文件,只有上面這兩個,沒有第三個。** 另外兩件事常被誤認為是新的一份文件,其實都不是:

| 這件事 | 它其實是什麼 | 要維護幾份文件 |
|---|---|---|
| 加入使用者提供的圖片 | 對階段一那份檔案的**加工** —— 同一個檔案、版本號 +1 | 仍然一份 |
| 發布成 artifact | 階段一那份文件的**發布通道** —— 內容完全相同,只是多一個可分享的網址 | 仍然一份 |
| 做列印版 | **真的是第二份文件**,為紙本重新編排過 | 兩份 |

所以不管加了圖、還是發布了 artifact,要維護的都還是詳細版一份。**只有使用者要列印本,才會第一次出現「兩份要同步」的問題** —— 那也是為什麼列印版要等內容定案。列印版做出來時,會沿用詳細版當時的那批圖。

**內容還在修改的階段絕對不要同時維護兩份。** 改一個時間、換一家餐廳都要改兩個檔案,不但成本翻倍,還很容易出現兩份內容不一致。先把詳細版的內容改到定案,再談排版成紙本。

如果使用者一開始就說要列印本,還是先做詳細版,並告訴他「內容確認後再排列印版,避免內容還在改的時候維護兩份」。

## 階段一的製作順序

檔名一律含**目的地 + 日期 + 版本**(例如 `上海行程_20260904-0908_v1.html`)。使用者會累積多個版本,檔名分不出來就會拿錯份。

### 在 claude.ai 聊天介面

1. 先用 `view` 讀 `/mnt/skills/public/frontend-design/SKILL.md`,取得視覺設計準則(這一步不能跳過,跳過就會做出樣板感的東西)。
2. 用 `create_file` 產出**單一 HTML 檔案**,CSS 與 JS 全部內嵌在同一檔案。
3. 存到 `/mnt/user-data/outputs/`。
4. 對照 `references/output-checklist.md` 逐項檢查(含編輯標準那一節)。
5. 呼叫 `present_files` 交付。

### 在 Claude Code

**預設交付本地 HTML 檔案。要不要另外發布成 artifact,一定要先問過使用者。**

1. 用 `Skill` 工具呼叫 `artifact-design` 取得視覺設計準則(同樣不能跳過)。
2. 用 `Write` 寫出**完整的 standalone HTML 文件**(細節見下方)。
3. 對照 `references/output-checklist.md` 逐項檢查(含編輯標準那一節)。
4. 在回覆裡給出**檔案的完整絕對路徑**,讓使用者可以直接開啟。
5. **在同一則回覆裡問一句**:要不要另外發布成 artifact(會得到一個可分享的網址,方便轉發給同行者、秘書或司機)?
   - 使用者同意 → 用 `Artifact` 發布,給 `favicon` 與一句 `description`,並交付網址。之後改版**重用同一個檔案路徑**重新發布,網址不變。
   - 使用者沒回答、或說不用 → **就只有本地檔案。不要自己發布。** 沉默不等於同意。
   - 使用者一開始就說要網址 → 直接發布,不用再問一次。

發布 artifact 會把整份行程放到一個可以分享的網頁上,裡面可能有飯店訂房編號、聯絡人電話、費用這類使用者不一定想外流的資訊 —— 這就是為什麼要先問,而不是預設幫他上傳。

#### 存哪裡

**絕對不要存到 session 的暫存/scratchpad 目錄。** 那是給中間產物用的,會被清掉,而行程手冊是使用者要留下來的東西。

依序判斷:

1. 使用者指定了路徑 → 用他指定的
2. 沒指定 → 存在**專案根目錄**(含 `.claude/` 的那一層)下的 `itineraries/` 子目錄,不存在就建立。用專案根目錄而不是「目前工作目錄」,是為了讓位置可預測 —— 從子目錄叫用時不該散落在子目錄裡
3. 檔名照原規則含目的地 + 日期 + 版本

**行程手冊裡有訂房編號、聯絡人電話、完整費用,不該進版本控制。** 如果 `itineraries/` 位於一個 git repo 裡,確認它已被 `.gitignore` 排除;沒有的話先加進去再寫檔,並在交付訊息裡說明你加了這一行。不要讓使用者在幾天後才發現自己的行程被 commit 上去了。

#### 必須是完整的 standalone 文件

因為交付的是本地檔案(用 `file://` 直接開),下面這幾項缺一個就會實際壞掉:

```html
<!doctype html>
<html lang="zh-Hant">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>…</title>
<style>/* 全部內嵌 */</style>
</head>
<body>
…
</body>
</html>
```

- **`<meta charset="utf-8">` 是必須的。** 本地開檔沒有 HTTP header 指定編碼,瀏覽器會自己猜;繁中 Windows 猜錯就是整份中文與日文變亂碼。這是最容易壞、也最容易漏的一項。
- **`<html lang>`、`<head>`、`<body>` 都要寫齊。** 瀏覽器雖然容錯,但不要依賴容錯。
- **字體用系統字體堆疊,不要外連 Google Fonts 或任何外部資源。** 離線與沒網路時都要能正常顯示 —— 這跟原本「CSS/JS 全部內嵌、離線可讀」的要求一致。

## 必含區塊

### 1. 製表資訊
製表日期與版本標記(例如 `v2 · 2026-08-23 製`)。行程會改版,沒有版本標記使用者會分不清手上哪份才是最新。

若問卷的 H 類問到**有不宜寫入的內容**(價格、內部人事、行程真正的目的),要據此處理:

- 這些內容從文件中**整段隱去**,不是改成模糊寫法(「費用約中等」比寫出金額更容易引起猜測)
- 只有部分讀者不宜看到時,問使用者要不要另外做一份**對外版**(隱去敏感區塊),而不是在同一份裡混雜
- 對外版要在製表資訊標明是對外版,避免與完整版混淆

### 2. 行程總覽
目的地、日期、天數、對象(含每位同行者的身分角色)、事由。

### 3. 一頁式速查總表
每天一行,濃縮該日重點:住宿地、主要行程、當日固定錨點。讓人不用翻完全部細節就能掌握整趟輪廓,也方便單獨列印或轉發。

同一區塊要附一份**全程硬約束清單**:把散落在各天的「不能誤的時間點」集中列出(幾月幾號幾點前一定要抵達哪裡、需要帶什麼證件),通常只有 2-4 項,但這是整份手冊最不能出錯的地方。

### 4. 每日時間軸

**若同行者當天走不同行程,時間軸要分軌呈現。** 例如老闆去展會、老闆娘去購物,不可以混成一條讓人看不出誰去哪裡。每一軌標明是誰(用問卷拿到的身分角色,例如「老闆＋特助」「老闆娘」),各自有自己的移動行、用餐、車輛安排;分開與會合的時間點要明確標出來。車輛不夠時要註明哪一軌用車、哪一軌搭大眾運輸或另外叫車 —— 兩軌同時要用同一台車是實際會發生的排程錯誤。


每一天的開頭放**一句話定調**,講清楚這天是什麼性質(例如「今天唯一的硬時間是傍晚的登船」「今天最滿也最趕,早上請務必提早出門」「下午都在同一棟建築裡,不必再移動」)。

每個項目要標明:
- **精確到分鐘的當地時間**(跨時區標明是哪一地的時間;跨日抵達標 `+1`)
- 地點名稱與地址
- **地圖連結** —— 當地可用 Google Maps 時附連結;不可用時(中國大陸等)改寫完整當地語言地址 + 樓層店號,見下方「地圖連結」一節
- 室內 / 戶外標籤
- **完整營業時間,不只是「當天營業」**。有午市晚市分段的要分開寫(例如「營業 11:00–14:00、17:00–21:00」),使用者才有辦法自己判斷這一格能不能挪時間。查不到要標註「未能確認」並附已確認營業的備選
- 門票或人均消費,以及來源(例如「人均 約 RMB 290–345(大眾點評)」)
- 是否需事前預約、預約管道與最晚訂票時間
- **訂位或入場時要特別交代的事** —— 例如「務必指定 9 樓的餐廳,避免被帶到一樓酒廊」、「需核驗身份,證件務必隨身」。這種細節只寫在附錄沒有用,要寫在會用到的那一格
- **狀態徽章** —— 每一格都標明目前的訂位/購票狀態,見下方
- **這一格的實際人數**(若與同行總人數不同)—— 見下方
- **票價要對回行程當天的類別** —— 平日票、假日票、季節票價不同的地方,要算出行程當天適用哪一個並寫出理由。例如「門票平日 RMB 98、週末及假日 RMB 128 —— 9/5 為週六,適用 128」。只寫「門票 98–128」等於沒查
- **分時段入場的要寫出適用場次** —— 例如「分四時段入園(9–11／11–13／13–15／15–17),行程 10:50 入園,適用 09:00–11:00 場次」。只寫「需預約」使用者不知道要訂哪一場
- **購票管道要分「當地」與「境外」** —— 很多地方的官方管道是當地 App 或小程序,非當地居民辦不了或付不了款,要一併寫境外可用的平台。例如「購票管道為上博小程序／攜程,**境外用 Trip.com**」。這一項漏了,使用者會卡在付款頁面
- **會搶票的項目要寫開賣時間** —— 例如「官方每月 1 日中午 12:00 開放次月場次」。熱門特展、限量體驗、熱門餐廳都適用
- **實名制的要寫清楚「每個人都要各自辦」與需要的證件號** —— 例如「實名制入場,三人都要各自線上預登記,填台胞證號」。只寫「實名制」會讓人以為一個人登記就好

#### 狀態徽章:訂位狀態要標在那一格,不只在追蹤表

每一個需要訂的項目,**在時間軸那一格與該項目的介紹裡都標上狀態**,不要只放在訂位追蹤表 —— 使用者照著行程走的時候不會翻回追蹤表。

一套建議的徽章用語(依實際情況選):

| 徽章 | 意思 |
|---|---|
| `已預定 14:30` | 已訂好,並帶上確認的時間 |
| `已購票` | 票已買,分場次的要一併寫適用場次 |
| `待訂` | 還沒訂,追蹤表裡有截止日 |
| `不接受訂位` | 該店不收預約,要現場排 |
| `現場代排` | 由誰現場排隊(旅行社、秘書、當地窗口) |
| `旅行社已完成` / `秘書已處理` | 已委外並已完成 |

**時間軸開頭要放一個圖例**,說明這些徽章與項目類型的標記各代表什麼。**圖例本身要有「圖例」這個標題** —— 一排沒有標題的色點與詞彙,第一次看的人不知道那是什麼,會直接跳過。

#### 逐項人數:訂位人數不一定等於同行人數

如果某一格的實際人數與同行總人數不同,**一定要標出來**。實際會發生的情況:有人不參加某一餐、當地窗口或司機一起用餐、貴賓行程中我方陪同人數不同、某個活動有人不參加。

寫法:徽章帶人數(`已預定 3 位`),而同一天別的項目是 2 位時,兩邊都要標,讓差異看得出來。**只寫「已預定」而人數其實不同,訂位就會訂錯。**
- **固定錨點要明確標示為不可調整**,不能跟其他建議活動混在一起看起來都能換

**主行程每個時段只放一個定案**——你最推薦的那一個,附上為什麼推薦它。主時間軸要乾淨到可以直接照著執行、可以直接轉發給司機,不要在同一格塞 2-3 個並列選項讓人自己選。替代方案全部集中到獨立的備案章節(見區塊 9)。

每個項目都必須是**實際查得到**的真實店家(地點查詢或網頁搜尋工具,見 SKILL.md 環境對應表),不能是隨口舉例。查不到訂位資訊時,要註明具體的下一步(例如「建議由飯店禮賓部協助訂位」),不能停在「建議」兩個字。

#### 商務與接待類項目要用不同的欄位

上面那組欄位是為景點與餐廳設計的。**會議、拜訪、展會、接待這類項目要換一組欄位**,不要拿景點的欄位硬套:

- **會議 / 拜訪**:對方單位全名、部門、**聯絡人姓名與電話**、地點與樓層、報到方式(前台登記、需要證件、需要預先提供名單)、預計時長、我方出席者、要帶的東西(名片、伴手禮、簡報檔、文件)
- **展會**:展會全名與屆數、會期、目標展區或館別及其位置、登錄或報到處在哪、參展證取得方式、預計停留、離場的接送安排
- **接待貴賓**:貴賓的班機與航廈、**我方接待人員名單與各自負責的時段**、宴請規格(包廂、席次、實際人數含陪同)、送禮/致詞/合影/參訪的時點與負責人
- **商務空檔**:依問卷的空檔偏好安排(回飯店休息 / 商務中心或飯店辦公 / 參觀 / 保留彈性),並標明可用的辦公空間在哪

這些項目通常就是行程的固定錨點,要一併標為不可調整。

#### 二擇一的項目要寫出「選了之後會怎樣」

某一格是兩個方案擇一時(「飯店休息 **或** 提前去機場逛街」),不能只寫「二擇一」就結束。**每個選項各給一句後續影響**:

> **若選飯店休息** —— 飯店的早茶或江景陽台都在樓內,是最省力的收尾方式,不需要換裝出門、也不必再叫車。
> **若選提前去機場** —— 把 10:00 出發往前挪一小時,就有兩個多小時可以慢慢走,不會壓到班機。

沒有這兩句,使用者當天早上還是得自己想一遍。

#### 移動要獨立成行,不是塞在項目的欄位裡

每一段移動都佔時間軸上獨立的一行,連 5 分鐘的車程也要列:

> 13:05—14:00 前往和平飯店(車程 40–50 分)
> 17:00—17:30 前往飯店(車程 20–30 分)
> 20:00—20:05 回飯店(車程 3 分)

這樣做有三個實際好處:時間軸可以直接**驗算**(每一行的結束時間就是下一行的開始時間,對不上一眼就看到);司機可以直接讀這幾行;使用者要調整行程時知道動一格會擠壓到什麼。

移動那一行要寫的內容依交通方式而定:
- 包車/計程車 —— 車程分鐘數(車流量大的路段給區間,例如「40–45 分」並註明原因)
- 大眾運輸 —— 線名、上下車站名、分鐘數、票價,查得到就連出口編號一起寫(例如「地鐵東西線 大通站 → 宮之澤站,約 17 分,¥290;3 號出口步行 7 分」)
- 步行 —— 分鐘數,以及有沒有遮蔭/上坡等會影響體力的條件

#### 步行可達的多點要串成一條動線

幾個彼此步行可達的項目,寫成連續的一段並明確講出「中間不需用車」:

> 14:30–15:30 百達翡麗上海源邸(專人中文導覽,需預約)
> 15:30–16:00 外灘源 33 號 · 英式大花園
> 16:00–16:30 沿黃浦江散步賞萬國建築群 & 咖啡
> ▸ 三段全在步行範圍內,中間不需用車 —— 是全程最不需要交通的一段下午

這比把三個點各自列成獨立項目、各自寫一次交通有用得多,而且使用者一眼就知道這段的彈性在哪。

#### 大型場地要給內部動線

展館、大型博物館、機場、大型商場這種「進去之後還要找路」的地方,光給地址不夠,要寫進去之後怎麼走:

- 目標區域是哪幾館/哪幾層,它們在場地的哪一側
- 報到或登錄在哪裡(常常跟目標展區不同側)
- 大眾運輸出入口在哪一側
- 其他區域有什麼(讓使用者臨場能決定要不要多看)
- **離場時的接送安排** —— 例如「離場時請司機提前在允許停靠的臨停區等候,展期會場周邊很難臨時叫車」


### 5. 航班資訊
去程/回程班號、航空公司、起降時刻(標當地時間)、航廈、艙等、飛行時間、票價(已訂位就填實際票價,未訂位填查到的價格區間)、**該艙等的托運與手提行李額度**(問卷問到有特殊裝備時,一併確認該裝備的托運規定與費用)。
已訂位就填實際班號;未訂位要列出查到的候選航班,**不要留空白**。

**抵達時刻一律用航空公司公布的當地時刻,不要自己用「起飛時間 + 飛行時數」加算。** 跨時區的加算幾乎一定會錯(時差、日光節約時間、跨日),而抵達時刻錯了會連帶讓當天整串行程與接機安排全部錯位。查到的時刻表本身就同時給了起降兩地的當地時間,直接抄。

### 6. 住宿資訊

基本欄位:飯店名稱、地址(含當地語言寫法)、電話、Google Maps 連結、入住與退房時間、開幕或整修年份、規模(客房數)。

**房型表**要有:房型名稱、面積、床型、房價、間數、備註。有欄位查不到或還沒確認,就寫「待確認」並註明「請以訂房確認信為準」——不要留空白,也不要自己填一個看起來合理的數字。

另外三塊是把飯店當成整趟行程的樞紐來寫,一般行程單都沒有,但很實用:

**與各行程地點的車程** —— 列出飯店到主要行程點的車程(例如「離展場 35 分」「離最近的商場 3 分」)。使用者評估飯店選得好不好、以及每天要留多少交通時間,靠的是這張表。

**行程對應表** —— 每天幾點從飯店出發、去哪裡、車程幾分、幾點回飯店:

> 9/4 17:30–18:00 check in;18:10 晚餐(車程 3 分)
> 9/5 10:30 出發世博文化公園(10–15 分);21:20 回飯店
> 9/7 08:30 出發國家會展中心(35 分);19:30 回飯店

一眼就能看出哪天最晚回來、哪天出門最早,對安排飯店設施與體力分配很關鍵。

**飯店設施的使用建議** —— 不要只列出有什麼設施,要說明**哪個設施適合排在哪一天**,以及為什麼:

> 「水療與高空泳池最適合 9/5 或 9/6 晚間回房後;9/7 展會日結束較晚,不建議」
> 「飯店的下午茶與 9/4 的行程內容重疊,建議改排在 9/8 上午,或當作宵夜酒吧使用」

飯店設施也是行程的一部分,要納入排程判斷,不是附在最後的設施清單。

### 7. 司機 / 接送通知摘要(若適用)

設計成**可以直接複製轉發給司機**的形式:幾點在哪裡接、送到哪裡、車上有幾位、聯絡窗口姓名電話。去程與**回程返抵後**的安排都要有。未確定時要註明下一步動作,不能只寫「待補」。

三個容易漏的實務要求:

- **地址要用司機看得懂的語言。** 當地司機看不懂中文地址,要寫當地語言全稱(含門牌、樓層、哪個出入口或臨停區);台灣司機才用中文。如果司機與使用者語言不同,雙語並列。
- **每天一份,不要只給一份總表。** 實務上是每天前一晚把當天那份轉發給司機,所以要按日切開、每份自成一體(當天所有接送時點 + 地址 + 人數 + 聯絡人),不是要司機自己從整趟總表裡挑出今天的。
- **包車的話註明今天的用車起訖與時數**,讓司機與使用者都清楚會不會超時。

### 8. 訂位狀態追蹤表
把所有需要訂的項目列成一張表 —— 除了機票、飯店、餐廳、門票、包車,**也包含需要安排的人**:導遊、口譯、攝影、當地窗口,以及需要事前預約的導覽場次。每列標明:
| 項目 | 狀態 | 訂位編號 | 負責人 | 最晚要訂的日期 |

狀態用「已訂 / 待訂 / 已委外」。這是實務上使用者最常拿來用的一塊,不要省略。

### 9. 備案(獨立成章,不是主行程的附註)

備案是一個**獨立章節**,不是塞在每日時間軸裡的括號。分成「餐廳備案」與「景點備案」兩組,每組依性質排序,篇幅可以佔到整份文件的三分之一——這不是湊字數,備案寫得夠好,行程才有應變能力。

每個備案要有的欄位,和主行程的項目**一樣完整**(介紹、地址、營業時間、人均或票價、車程、Maps 連結),另外必須多一項:

- **可替換哪一段** —— 明確寫出這個備案是用來取代哪一個時段或哪一個項目,以及為什麼。例如:
  - 「適合 9/6 午餐的同棟替代」(同一棟樓 3F/4F,換了不用重排交通)
  - 「9/5 恆隆 66 下午行程的延伸晚餐」(位置直接接得上)
  - 「需要 2-3 小時的套餐制餐廳,適合取代 9/6 或 9/7 的一整段,**而不是硬插進現有行程**」

最後一種寫法特別重要:**要寫清楚這個備案不能怎麼用**。只說「可以去這家」而不說它會吃掉多少時間,使用者換上去就會把當天後面全部擠爆。

備案要涵蓋三種觸發情境:
1. **天氣** —— 雨天、高溫、颱風的室內替代
2. **臨時關閉/客滿** —— 訂不到位、休館、展期變動時的同級替代(優先找同棟或鄰近的,交通不用重排)
3. **行程延誤或提早結束** —— 例如展會提早結束時最順路的休息選項

備案分**三組**,不是兩組:

- **餐廳備案**
- **景點與休息備案**
- **交通備案** —— 這一組最常被忘記。替代的**移動方式**,不是替代的地點:走不動時同一段路有什麼代步選擇(觀光車、接駁車、計程車)、有什麼要注意的(「16:00 起該站改停東側」)。對「偏好較少步行」的同行者,這一組比多一家餐廳有用。

每個備案除了「可替換哪一段」,還要有這四項:

- **可用性前提** —— 這個備案現在能不能直接換上去。需要事前預約、實名制、購票的,要標明**目前的狀態**:「實名制,需線上預約並攜帶證件 —— **本次未申請**」。臨時要換的時候,使用者才知道行不行,而不是到了門口才發現進不去。
- **對同行者的適用性** —— 備案也要做限制回核。「走道是大片草坪與平緩步道,比外灘擁擠的人行道對長輩更友善」、「全程坐著躺著,零走路負擔」。
- **在整趟行程裡的角色** —— 「整趟唯一『純放鬆』的選項」、「與外灘不重複:外灘是走進老建築看細節,這裡是隔江看建築群全貌」。
- **這個備案本身的不足與補救** —— 例如「園內餐飲以咖啡輕食為主,想吃正餐建議走到對面商場的某家」。備案換上去之後產生的新問題,一併解決掉。

備案裡不可以出現「改為室內行程」「另尋餐廳」這類等於沒有備案的句子。

### 10. 費用估算摘要

機票 / 住宿 / 餐飲 / 市內交通 / 門票與活動 / 雜支分項概估區間。即使預算是「高端不設限」也要給,讓使用者知道數量級。

**估算方法要逐項算出來,不要憑感覺給一個籠統數字:**

| 項目 | 算法 |
|---|---|
| 機票 | 艙等票價 × 人數。已訂位用實際票價 |
| 住宿 | 房價 × 間數 × 晚數。多種房型分開算 |
| 餐飲 | **逐餐的人均 × 人數,再加總** —— 不要用一個籠統的「每日餐飲預算」。一頓米其林套餐與一頓小吃差十倍,平均掉就失去意義 |
| 市內交通 | 包車:日費 × 天數(註明時數制與超時費率)。大眾運輸:各段票價 × 人數加總。計程車:依趟數與距離估 |
| 門票與活動 | 逐項加總,含需預約的體驗與導覽 |
| 雜支與伴手禮 | 另列一項並給區間,不要併進其他項目 |

呈現要求:

- **分項 + 每人總計區間 + 全團總計**三層都要有
- **已訂與未訂分開標**:已訂的是確定金額,未訂的是估算。混在一起會讓使用者以為整個總額都已鎖定
- 一律給**區間**而不是單一精確數字(除了已訂的實付金額)
- **某一項的不確定性大到會影響總計時,要把它反映在區間寬度上,或在總計旁註明主要的不確定來源。** 只在那一列加註解不夠 —— 使用者看的是總計。例如票價是用內插估算而可能差兩成時,總計的上緣要含得住那個誤差,或在總計下方寫「最大的不確定來源是台鐵票價(估算值,實際可能高出約 25%)」
- 標明**幣別、換算匯率、匯率查詢日期**,否則過幾天就失真
- 若問卷問到需要請款憑證,註明哪些項目會有發票或收據
- **估算跟使用者給的預算差距顯著時要主動講出來**,不要讓他自己比對。比預算低很多 → 明講「不需要為了花完預算而升級」,並依**對這趟行程目標的實際幫助**排序給出升級選項(不是依價格高低)。比預算高 → 明講超出多少、哪幾項是主因、可以砍哪裡。使用者給預算是為了得到判斷,不是為了拿到一個剛好塞滿預算的數字

### 11. 行前準備清單
用可勾選的清單形式:證件(護照效期、簽證、目的地專屬證件、影本備份)、電壓與插座轉接、依查到的實際天氣給的衣物建議、常備藥品、當地付款方式準備(現金/信用卡/行動支付)、上網方案、需要在出發前安裝好的 App(當地地圖、叫車、行動支付、必要時 VPN)。

**商務或接待行程要另外加一組**:名片、伴手禮(數量與收禮對象)、簡報檔與轉接線材、要列印的文件、參展證或邀請函、正式場合的服裝、送禮清單與各自的贈送時點。這些是商務行程真正會忘記帶的東西,一般旅遊的打包清單不會涵蓋。

### 12. 實用資訊附錄
簽證與入境規定、時差、電壓與插座型式、通訊(SIM/eSIM/分享器)、貨幣與付款方式、基本當地用語。

另外必含一項**網路與服務可用性**(這一項最常被漏掉,但影響落地後的每一件事):

- 哪些常用服務在當地**不能用**(Google 全系列、Line、Facebook、Instagram、WhatsApp、常用地圖與叫車 App 都可能受限),以及當地的替代品叫什麼
- **付款方式的實際限制** —— 國際信用卡在當地的接受度、是否幾乎只收當地行動支付(支付寶、微信支付、當地錢包)、現金需求、需不需要事先綁定或註冊
- 叫車怎麼叫(當地 App 名稱、是否需要當地手機號碼註冊、飯店代叫)
- 是否需要 VPN,以及要在出發前就裝好(落地後可能就下載不了)

這一節要依實際目的地查證後寫,不要套用通用模板。

這是基本盤。除此之外要**依問卷的內容偏好再生成 1-2 份主題附錄**(購物偏好 → 當地百貨專題;美食偏好 → 依菜系與價位分類的餐廳專題;文化古蹟 → 串成步行動線並標明休館日)。主題附錄的每一項都要寫明「接回行程的實際用法」,不是資料匯編。做法見 `references/editorial-standards.md` 的「主題附錄」一節。

附錄的項目要跟主行程與備案**交叉引用**,加一個「順道」欄位:

> **上海 IFC 國金中心** 陸家嘴 · 世紀大道 8 號
> 順道 4F 甬府尊鮮(9/6 午餐)、3F 老吉士酒家(備案)

這種交叉連結會讓整份手冊變成一張網,而不是幾個互不相干的孤島 —— 使用者臨場想改行程時,看得到哪些選項本來就在附近。

### 13. 緊急頁
獨立成一塊,**要能單獨列印帶著走**:
- 當地報案與救護電話
- 鄰近行程地點的醫院
- 我國駐外館處與旅外國人急難救助電話
- 保險公司 24 小時服務電話
- 信用卡掛失電話
- 飯店電話與地址(**當地語言寫法**,方便直接拿給計程車司機看)
- 使用者提供的緊急聯絡人

### 14. 資料來源與免責
一小段說明:資料整理自哪裡、哪些項目做過更正、哪些數字是什麼時候查的、哪些事情出發前要再確認一次。這不是免責套話,是把「這份文件的有效期限與已知弱點」講清楚。

## 撰寫細則

### 單一時間軸項目的完整範例

以下是**格式與資訊密度的示意**,說明一個時間軸項目「寫完整」是什麼樣子。**內容本身是舉例,實際排程時每一個欄位都必須實際查證**,不可以照抄這裡的店名、票價或時刻:

> **14:05–14:30** → 前往白色戀人公園
> 地鐵東西線 大通站 → 宮之澤站,約 17 分,¥290;3 號出口步行 7 分
>
> **14:30–16:00** ｜ 室內 ｜ 白色戀人公園
> 北海道札幌市西區宮之澤 2-2-11-36 ｜ [Google Maps](https://www.google.com/maps/place/?q=place_id:XXXXXXXX)
> 營業 09:00–18:00(全年無休,最後入館 17:00)
> 門票 成人 ¥800,需事前線上預約指定時段,建議最晚出發前 3 天訂
> 訂票時 指定含工廠參觀路線的票種,只買庭園票進不去製造線
> 雨天無影響(全程室內)
> ▸ 排在午後是刻意的:這天上午是戶外行程,下午換到全室內,九月札幌午後日曬仍強。1 小時 30 分足夠走完製造線與庭園,不必再壓縮。

對照一下「寫不完整」會長什麼樣——這是要避免的:

> 下午 參觀白色戀人公園

差別不在文字多寡,而在**看完之後還需不需要自己再去查東西**。上面那份可以直接照著走,下面那份還要自己查地址、開放時間、門票、怎麼去、要不要預約。

注意上面範例的三個細節:移動自己佔一行(14:05–14:30),不是塞在項目欄位裡;營業時間給的是**完整時段**而不是「當天營業」;最後一行是**排程判斷**,說明為什麼排在這個時間、為什麼是這個長度。

### 地圖連結:先確認目的地能不能用 Google Maps

**這件事要先判斷,不要無條件貼 Google Maps 連結。** 部分地區的 Google 服務無法正常使用(中國大陸最典型,需要 VPN 才連得上),在那裡貼一整份 Google Maps 連結,使用者與當地司機一個都點不開,等於整份連結都是廢的。

判斷與處理:

- **當地可正常使用 Google Maps**(多數國家)→ 照下面的格式附連結
- **當地無法使用**(中國大陸等)→ **不要附 Google Maps 連結**,改成:
  - 地址寫**完整的當地語言全稱**(含省市區與門牌號),讓使用者可以直接給司機看或輸入當地地圖 App
  - 若查得到,補上當地常用地圖服務的名稱與搜尋關鍵字(例如高德地圖、百度地圖搜「店名 + 商場名」)
  - 商場或大樓裡的店家,一定要寫到**樓層與店號**(例如「國金中心商場 3F L3-19」),當地叫車與問路靠的是這個,不是座標

不確定當地能不能用時,用 `web_search` 確認,不要假設。

### Google Maps 連結格式(當地可用時)

每個景點/餐廳/飯店都要附連結,方便使用者或司機直接點擊導航:

- 有地點查詢工具、且查到 `place_id` 時(只有 claude.ai 有),用精準格式:
  `https://www.google.com/maps/place/?q=place_id:<place_id>`
- 沒有 `place_id` 時,用地點名稱與地址組成搜尋連結:
  `https://www.google.com/maps/search/?api=1&query=<地點名稱與地址,URL 編碼>`

## 排版與技術要求

- 用日期分頁籤或區塊區隔每一天,避免長篇條列文字堆疊
- 手機寬度可讀
- **可列印**:附 `@media print` 樣式。列印時日期分頁籤要全部展開,不能只印出當前那一頁
- **可離線**:出國後常常沒網路。地址、電話、營業時間都要以文字寫在頁面上,Google Maps 連結是額外便利,不是資訊本身的替代品

### 列印時展開分頁籤

日期分頁籤在螢幕上好用,但列印時如果只印出當前那一頁,整份手冊就廢了。分頁籤的實作要讓列印樣式能把全部日期展開:

```css
@media print {
  .day-tabs { display: none; }              /* 隱藏頁籤按鈕本身 */
  .day-panel { display: block !important; } /* 所有日期一律展開 */
  .day-panel { break-after: page; }         /* 每天各自一頁 */
  .day-panel:last-of-type { break-after: auto; }  /* 否則最後會多印一張白紙 */
  .emergency-page { break-before: page; }   /* 緊急頁獨立一頁,方便單獨撕下帶著 */
  a[href^="http"] { text-decoration: none; color: inherit; }
  /* 不要印出長網址:紙本上的 Google Maps 連結是無效資訊,
     地址與電話已經以文字寫在頁面上了 */
}
```

若用 JS 控制分頁籤切換,要確認**列印時不依賴 JS 狀態**(用 CSS 覆蓋 inline style,或監聽 `beforeprint` 先把全部面板展開)。


## 交付後的回覆

用環境對應的交付方式(`present_files` 或 `Artifact` 發布)交付即可,**不需要在回覆中把整份行程再貼一次文字版**。但回覆不能只有一句「已完成」,以下五件事要講:

1. **哪些資訊目前是預設值或估算** —— 使用者沒提供、由你採合理預設的項目,逐項列出來讓他知道要不要修正
2. **訂位追蹤表裡最近的截止日** —— 哪一項最快要訂、最晚什麼時候要訂完。這是使用者離開對話後第一個要行動的事
3. **還需要使用者提供什麼** —— 司機聯絡窗口、訂位編號、證件狀態這類只有他有的資訊
4. **查證時發現的矛盾或風險** —— 營業時間與行程衝突、資訊來源不一致、資料日期較舊需要出發前再確認的項目。這些在文件裡有標,但回覆裡要再提一次最關鍵的幾項
5. **驗收清單裡沒做到的項目** —— 如果有任何一項決定不補,說明是哪幾項與為什麼。**不可以默默略過**
6. **主動提出接下來可以做的三件事**,不要等使用者自己想到。用一個可複選的提問(Claude Code 用 `AskUserQuestion` 的 `multiSelect`)問他要哪些:
   - **加入你自己拍的圖片** —— 見下方「加入使用者提供的圖片」一節
   - **發布成 artifact 取得可分享網址** —— 見上方交付流程
   - **做 B5 列印版**(一個項目一頁、頁碼頁眉、適合裝訂)—— 內容定案後才做
   - **都不用,先看內容**

   第三項尤其要主動講。**使用者不會知道有列印版這個選項,除非你告訴他。** 但同時要說明「等內容確認後再做,避免內容還在改的時候維護兩份」。

不要在回覆裡重複行程細節,也不要用形容詞誇獎自己的產出。

## 加入使用者提供的圖片(選用)

**這是對詳細版那個檔案的加工,不是新做一份文件。** 改的是同一個檔案、同一個路徑,只有版本號 +1。

手冊預設是純文字的。圖片有三種來源,規則不同:

| 來源 | 可不可以用 | 條件 |
|---|---|---|
| 使用者自己提供的檔案 | ✅ 可以 | 交付後主動問他要不要加 |
| **明確標示自由授權的圖片**(Wikimedia Commons 的 CC BY / CC BY-SA / CC0、公有領域) | ✅ 可以 | **必須下載後內嵌,並在圖說標明「作者／授權條款,來源」**。例如「(照片:shankar s.／CC BY 2.0,Wikimedia Commons)」。用之前先問使用者要不要 |
| 一般網路圖片、社群貼文、店家官網照片 | ❌ 不可以 | 版權不明或明確保留權利。**不要用,也不要熱連** |

**任何情況下都不要熱連(hotlink)**:外部連結離線失效、多半違反對方的使用條款、而且對方換圖你的手冊就跟著壞。要用就下載後內嵌。

自由授權的圖片解決一個實際問題:使用者沒拍到、或還沒去過的地點(景點、飯店外觀、展館)也能有圖。但**授權標註是義務不是禮貌** —— CC BY 與 CC BY-SA 都要求標示作者與授權條款,漏標就是違反授權。找不到明確授權標示的圖,一律當作不能用。

### 步驟

#### 內嵌還是相對路徑

**兩種都可以,依使用者怎麼用這份手冊決定,交付時問清楚:**

| 做法 | 優點 | 代價 |
|---|---|---|
| **base64 內嵌** | 真正的單一檔案 —— 可以直接寄給別人、複製到任何地方、發布成 artifact 都不會破圖 | 檔案會變很大(84 張照片約 9.5MB),編輯時不好處理 |
| **相對路徑 + 圖庫資料夾** | HTML 檔小、圖片可以個別替換 | 搬移時要連資料夾一起搬,只複製 `.html` 會全破;發布成 artifact 讀不到 |

**要寄給別人或發布成 artifact → 用 base64 內嵌。只有自己在本機看、而且會反覆換圖 → 用相對路徑。** 不確定就問使用者:「這份手冊你會寄給別人嗎?」


**行程手冊裡有訂房編號、聯絡電話、完整費用、緊急聯絡人,所以輸出位置一律被 `.gitignore` 排除,不進版本控制。** 這是固定的,不是要判斷的事。

(如果使用者主動說要把手冊複製到別處做版本控制,那是他手動處理的事,不是這裡的流程。真的問起來,提醒他三件事就好:檔名去掉版號讓 git 管版本、base64 改成相對路徑否則每版重存整批圖且 diff 讀不了、repo 必須是私有的。)

用 base64 時仍然照下面建立資料夾放原始檔 —— 原圖要留著,之後改版或做列印版才不用重新要一次。

**1. 建立資料夾。** 資料夾用**行程識別名(目的地 + 日期),不帶版號**;HTML 檔名才帶版號:

```
itineraries/
  liushidan-daylily-20260905-0906/        ← 圖庫,不帶版號
    pics/
      我拍的.jpg
      cc/                                 ← 自由授權圖與授權記錄
  liushidan-daylily-20260905-0906-v1.html
  liushidan-daylily-20260905-0906-v2.html
  liushidan-daylily-20260905-0906-print-v1.html
```

**資料夾絕對不要帶版號。** 理由跟版控無關,是改版成本:一趟行程只有一份圖庫,v1 → v2 不該複製一整份圖片、也不該改資料夾名(改了舊版就斷圖)。列印版與詳細版共用同一份圖庫,同理。

一趟行程一個資料夾,不同行程不會混在一起。`itineraries/` 已被 `.gitignore` 排除,所以圖片也不會進版本控制。

**自由授權的圖片要分開放,並留一份授權記錄。** 使用者自己的圖放 `pics/`,你抓來的自由授權圖放 `pics/cc/`,並在 `pics/cc/_licences.json` 記下每一張的完整出處:

```json
[{ "file":"六十石山-全景.jpg", "commons_title":"File:六十石山 panoramic, August 2017.jpg",
   "licence":"CC0", "licence_url":"http://creativecommons.org/publicdomain/zero/1.0/deed.en",
   "author":"Jason Zhang", "credit":"Own work",
   "page":"https://commons.wikimedia.org/wiki/File:...", "desc":"...", "kb":428, "w":1600, "h":766 }]
```

理由:圖說裡只寫得下「作者／授權」,但授權合規需要能追溯到原始頁面。**日後有人質疑、或要把圖挪去別的文件用,這份記錄就是憑據。** 分資料夾則讓「哪些是使用者的、哪些是我抓的」永遠分得清楚。

**2. 告訴使用者資料夾的絕對路徑**,請他把圖片放進去,並給命名指引:

- 用**看得出是什麼的名稱**:地名、設施名、飯店名 + 房型。例如 `羊蹄山-京極展望.jpg`、`ひらふ亭-溫泉展望客房.jpg`、`小樽運河-藍調.jpg`
- **不要用 `IMG_1234.jpg`** —— 那樣你只能靠開圖猜,而且使用者之後自己也分不出來
- 同一個地點多張,用 `-1`、`-2` 結尾
- 格式 jpg / png / webp。單張建議長邊不超過 2000px、檔案不超過 2MB;整份手冊的圖片總量建議控制在 20MB 內,再往上瀏覽器開起來會明顯變慢

**3. 使用者說放好了 → 逐張實際看過。** 用 `Glob` 列出檔案,然後**用 `Read` 把每一張圖真的打開看**。不要只憑檔名判斷內容 —— 檔名可能寫錯、可能與實際拍到的東西不符,而擺錯位置比沒有圖更糟。

**4. 整理成一張表給使用者看**:檔名 / 你實際看到的內容 / 建議放哪裡 / 為什麼。

**5. 每張圖給一個推薦位置 + 一到兩個備選**,讓使用者選。這跟主行程「單一定案 + 備案」是同一個精神:你給判斷,他做決定。

可選的位置類型:

| 位置 | 適合什麼圖 |
|---|---|
| 該日時間軸的那一格旁邊 | 那個景點/餐廳/飯店的實景 |
| 該日開頭的主視覺 | 最能代表那一天的一張 |
| 住宿或餐廳卡片內 | 房型、店面、招牌菜 |
| 主題附錄的圖集 | 同一主題的多張(例如同一座山的五個方位) |
| 一頁式速查總表旁 | 整趟最具代表性的一張 |
| 不使用 | 重複、模糊、或與行程無關的 |

版面選項:**單張寬幅** / **並排兩張** / **小縮圖列**。不要做 JS 燈箱或輪播 —— 增加壞掉的機會,而且列印時會失效。

**6. 使用者選定後插入。** 要求:

```html
<figure>
  <img src="hokkaido-yotei-20260924-0930/pics/羊蹄山-京極展望.jpg"
       alt="清晨的羊蹄山,從京極町方向拍攝,山頂受朝陽照射呈橘紅色"
       loading="lazy" width="1400" height="670">
  <figcaption>9/28 05:31 京極 · 朝燒(モルゲンロート)</figcaption>
</figure>
```

- **相對路徑**,不要絕對路徑(絕對路徑一搬家就斷)
- `alt` 寫**實際看到的內容**,不是檔名。這是給讀螢幕的人與圖片載入失敗時看的
- `figcaption` 寫這張圖在行程裡的意義(哪一天、哪個時刻、什麼現象),不要只重複地名
- CSS 要有 `img{max-width:100%; height:auto}`,不然大圖會撐破版面
- `loading="lazy"` 讓圖多的時候不會一次全載
- **`width` 與 `height` 屬性要寫上實際像素**,瀏覽器才能在圖載入前先保留位置,不會邊載邊跳版

**7. 版本號 +1,更新製表資訊**(例如 `v1` → `v2`,並在製表資訊註明「v2:加入 12 張使用者提供的圖片」)。

### 兩件必須告訴使用者的事

- **圖片是外部檔案,不在 HTML 裡面。** 搬移或寄送這份手冊時,**要連同圖庫資料夾一起搬**,只複製 `.html` 會變成一堆破圖。
- **之後若要發布成 artifact,相對路徑讀不到。** 那時圖片得改成 base64 內嵌(受 16MB 頁面上限約束)或用 artifact 的 asset 上傳機制。要發布就先講,不要交付之後才發現圖全破。

### 列印版與圖片

紙本比螢幕更需要圖片。若使用者要做列印版且已經提供圖片,列印版是把圖用得更完整的地方 —— 一個項目一頁時,那一頁就放該項目的圖。

## 階段二:列印版(使用者確認內容後才做)

列印版**不是把詳細版換個樣式**,是為紙本重新編排。做法跟詳細版完全不同 —— 詳細版是「內容自然流動、靠分頁籤分天」,列印版是「**每一頁是一個固定尺寸的容器,你決定每一頁放什麼**」。

### 固定頁面容器:這是列印版的核心技法

不要靠 `break-after:page` 讓內容自己斷。改成每一頁都是一個明確的元素:

```css
@page{ size:176mm 250mm; margin:0; }   /* ISO B5。JIS B5 是 182mm 257mm */

.page{
  position:relative;            /* 頁腳要絕對定位在頁內 */
  width:176mm; height:250mm;
  padding:13mm;                 /* 頁邊留白由容器自己負責,@page margin 設 0 */
  margin:0 auto 8mm;            /* 螢幕上頁與頁之間留間隔 */
  background:#fff;
  box-shadow:0 2px 12px rgba(0,0,0,.14);   /* 螢幕上像一張紙 */
  overflow:hidden;              /* 內容超出就是要改內容,不要讓它溢出 */
}

@media print{
  html,body{ background:#fff; }
  .page{
    margin:0; box-shadow:none;
    page-break-after:always; break-after:page;
  }
  .page:last-child{ page-break-after:auto; }  /* 否則最後會多印一張空白 */
  .toolbar{ display:none !important; }
}
```

要點:

- **`@page` 的 margin 設 0,頁邊留白交給 `.page` 的 padding。** 兩邊都設就會疊加,實際邊界比你想的窄。
- **`.page` 要有固定 `height`**,不是 `min-height`。這樣「一項一頁」才真的成立,而且你在螢幕上看到的分頁就是印出來的分頁。
- **`overflow:hidden`**:內容塞不進一頁時要**改內容**(縮短介紹、拆成兩頁),不要讓它溢出。溢出在螢幕上看不出來,印出來才發現被截掉。

#### 一定要附溢出自檢,不要靠眼睛逐頁看

`overflow:hidden` 會把超出的內容靜靜切掉,而你在螢幕上完全看不出來。**加一段自檢腳本,載入時自動檢查每一頁並把結果顯示在工具列上**(工具列列印時本來就隱藏,不影響紙本):

做法:對每個 `.page`,取頁腳 `.pfoot` 的 `offsetTop` 當內容上限(留 8mm 安全邊界),逐一比較子元素的 `offsetTop + offsetHeight`,超過就記下該頁與**超出的毫米數**。

```
FITCHECK OK / 42 pages          ← 綠色
FITCHECK OVERFLOW: #42(+3.5mm)  ← 橘紅色,並指出超出多少
```

用頁腳位置當上限比用 `scrollHeight` 準:內容壓到頁腳上也算溢出,而 `scrollHeight` 抓不到。

**交付列印版之前,FITCHECK 必須是綠色的。** 有橘紅就回去改那幾頁的內容,不要交付。

**但綠燈只代表「塞得進去」,不代表「版面是對的」。** FITCHECK 量的是高度,量不出文字被拆散、分隔符號掉在行尾、標籤與內容錯行這類問題。**交付前一定要實際打開看幾頁**,優先看含框、含表格、含圖的頁 —— 那些是最容易排壞的。綠燈給的是虛假的安心感。

#### 元件樣式不要選裸標籤

這是實際發生過、而且一次壞掉 35 個區塊的錯誤。當時的元件樣式寫成:

```css
.must b{ display:block; font-family:var(--mono); font-size:7.6pt; color:var(--alarm); }
```

意思是「`.must` 框裡的 `<b>` 是標題,所以獨立一行」。但內容裡的 `<b>` 還被用來做行內強調:

```html
<div class="must"><b>務必 · 出發前的五個時間點</b>
<b>今天 8/27</b>:四張台鐵票　│　<b>明天 8/28</b>:兩台機車</div>
```

結果**每一個 `<b>` 都變成獨立區塊**:日期各自佔一行、後面的 `:項目` 變成下一行開頭掛著一個孤立的冒號、`│` 分隔符號全部掉在行尾。全書 26 個「務必」框與 9 個「建議」框無一倖免,而 FITCHECK 還是綠燈(排壞只是變高,沒有超出)。

**規則:元件樣式一律選 class,不要選裸標籤。**

```css
.must  > .lbl { display:block; … }   /* 標題用自己的 class */
.must  b      { /* 什麼都不做 —— 留給內容做行內強調 */ }
```

已經寫成裸標籤時,最小的修法是限定第一個子元素:`.must > b:first-child{ … }`。

同一個陷阱適用於任何「把某個標籤在元件內重新定義」的寫法 —— `.card em`、`.tip i`、`ul.pts strong` 都一樣。**內容作者會用那些標籤做它們本來的事。**
- **`.page:last-child{page-break-after:auto}`** 一定要加,不加最後會多一張空白頁。
- 常用尺寸:ISO B5 `176mm 250mm`、JIS B5 `182mm 257mm`、A5 `148mm 210mm`、A4 `210mm 297mm`。**使用者說 B5 要問是 ISO 還是 JIS**,不確定就用 ISO 並在列印指引裡註明。

### Running footer:頁碼與章節名

HTML 沒有可靠的自動頁碼(`counter(page)` 只在 `@page` 的 margin box 裡有效,瀏覽器支援不一)。**直接在每一頁的 HTML 裡寫死章節名與頁碼**,反正頁面本來就是一頁一個元素:

```css
.pfoot{
  position:absolute; left:13mm; right:13mm; bottom:6mm;
  display:flex; justify-content:space-between; align-items:baseline;
  border-top:.2mm solid #DDE0E2; padding-top:1.6mm;
  color:var(--grey); font-size:7.4pt; letter-spacing:.06em;
}
```

頁腳左邊放章節名(`9/4(五)`、`備案`、`附錄 · 百貨`),右邊放頁碼。**改版時頁碼要重編**,這是列印版維護成本高的主因之一,也是為什麼要等內容定案。

### 螢幕上的列印指引與按鈕(不要省)

列印版會在瀏覽器裡被列印,而**使用者不會知道要調哪些設定**。頁面最上方放一條工具列,列印時隱藏:

```
上海五日手冊
B5 · 共 38 頁 · 列印請選「實際大小 100%」並勾選背景圖形
[ 列印 / 存成 PDF ]
```

- **「勾選背景圖形」是最關鍵的一句。** 瀏覽器預設不印背景色與底色,不勾的話所有色塊、標籤底色、分隔區塊全部消失,印出來會是一份看起來壞掉的文件。
- **「實際大小 100%」**:預設的「縮放以符合頁面」會把 B5 版面縮進 A4 裡,留下不對稱的白邊。
- 按鈕就是 `onclick="window.print()"`,別做更複雜的東西。
- 一併寫出**總頁數與紙張尺寸(含實際 mm 數)**,例如「ISO B5(176 × 250 mm)· 共 42 頁」。使用者才知道要不要雙面、要用什麼紙。
- 加一句**裝訂建議**:「建議雙面列印、短邊翻頁」。B5 手冊多半要裝訂,翻頁方向錯了整本就反了。
- 溢出自檢的結果也顯示在這條工具列上(見上方)。

### 頁面編排順序

1. **封面** —— 目的地、日期、天數、一行關鍵字副標(把這趟的亮點濃縮成幾個詞:「和平飯店的下午茶 · 亞洲最大玻璃溫室 · 米其林二星蔬食 · CIFF 傢俱展」)
2. **製表資訊與版本** —— 可以併在封面或封面次頁。**列印版特別需要**:紙本沒有檔案日期可看,手上有 v1 到 v4 時分不出哪份是最新
3. **一頁式速查總表** —— 38 頁的手冊沒有總覽頁,使用者每次都要翻
4. **航班與住宿** —— 通常各佔一頁
5. **每一天**:
   - **日扉頁**(一頁):日期大字、該日主軸、**「今日重點」框**、該日完整時間軸、徽章與類型的圖例
   - 接著該日**每個項目各一頁**
6. **備案** —— 每個備案項目也各一頁,欄位與主行程項目相同
7. **附錄與主題附錄**
   - 大章節(備案、附錄)**不需要獨立的分隔頁**,把群組標題放在該群組第一頁的頁首就夠了(「備案 · 餐廳」、「備案 · 景點與休息」、「附錄 · 百貨」)。獨立分隔頁在 38 頁的手冊裡是浪費紙
8. **緊急頁** —— **列印版比詳細版更需要這一頁**,因為紙本就是要帶著走。放在最後,設計成可以單獨撕下
9. **資料來源與免責**

### 日扉頁的「今日重點」框

這是列印版最有價值的一頁。不是重複時間軸,而是**該日的關鍵決策與提醒**,三到四條:

> 下午茶已預定 14:30,佔掉整個午後 —— 17:30 才 check in、18:10 就吃晚餐,是一路吃到晚上的節奏。
> 覺得太滿就把下午茶縮成 90 分鐘,先回飯店休息再出門吃晚餐。
> 和平博物館免費開放、自行參觀即可(專人導覽每日只有 12:00 一場),看完直接搭電梯上 9 樓,不必離開建築。
> 慶春樸門無法訂位 —— 旅行社會安排專人現場代排,18:10 入座。

這四條各自回答一個實際問題:今天的節奏是什麼、太滿的話怎麼調、這一站要注意什麼、訂不到位的那家怎麼辦。**寫成「你今天要注意什麼」,不是「今天要去哪」。**

### 日扉頁的時間軸用表格,不要用 flex

兩欄:**時刻 | 內容**。表格在列印時的欄位對齊比 flex 穩定得多:

```html
<table class="sched">
  <tr class="fly"><td class="tm">09:55</td>
      <td class="ev"><b>BR712 桃園 → 浦東</b><span class="note">12:05 抵達浦東</span></td></tr>
  <tr class="move"><td class="tm">13:05</td>
      <td class="ev"><b>前往和平飯店</b><span class="note">車程 40—50 分</span></td></tr>
</table>
```

每一列用**類型 class 上色**(`move` / `see` / `eat` / `fly`),內容欄用 `<b>` 主要資訊 + `<span class="note">` 補充。

### 圖例:類型與徽章都要說明

日扉頁的時間軸上方放一條圖例,否則顏色與徽章都是猜的:

> ● 移動　● 參觀 · 購物　● 用餐　● 航班 · 住宿　│　**已預定** = 旅行社已完成

四種列類型 + 徽章的意思。**每個日扉頁都要放一次** —— 使用者不會為了看圖例翻回第一天。

### 列印版的字級與色彩

- **字級一律用 `pt`,不要用 `px` 或 `rem`。** 紙本的絕對尺寸才有意義。
- **內文 9.5–10pt**。螢幕習慣的 16px(約 12pt)放在 B5 上太大,一頁塞不了東西。頁腳 7.4pt 左右,章節標題 13pt,日期大字可以到 27–36pt。
- **標題用襯線體、內文用無襯線體**是紙本常見的搭配(`"Noto Serif TC","Songti TC",serif` / `"Noto Sans TC","PingFang TC",sans-serif`),而且**一律用系統字體堆疊不外連**。
- **色彩用語意化 token,並給項目類型分色**:主色、強調色、**景點色**、**餐飲色**、灰、墨。類型分色讓翻頁時一眼認出這一頁是吃的還是看的。

```css
:root{ --deep:#1F5B52; --gold:#A8802B; --spot:#2F6B5F; --food:#A6503C;
       --grey:#71787F; --ink:#2E2E2E; }
```

- **滿版出血**:固定頁容器有 `padding`,想讓色帶延伸到頁緣就用負 margin 抵銷:`margin:-13mm -13mm 8mm`(上、左右抵銷 padding,下方保留間距)。

### 單項頁的固定骨架

每一頁照同一個順序排,讀者翻到第三頁就知道東西在哪:

1. **類型標籤** —— 景點 / 午餐 / 晚餐 / 下午茶 / 購物 / 展會 / 交通 / 備案
2. **名稱**(大字)
3. **副標** —— 位置 + 一句定位(「和平飯店 2F · 全中國第一家設在酒店內部的博物館」)
4. **圖片與圖說**(若有)
5. **背景** 或 **亮點** —— 一段散文
6. **第六層的標籤依項目類型換**:餐廳用「**推薦菜色**」(菜名 + 一句口感或定位)、景點與商場用「**重點**」、遊船或有多方案的用「**船型與費用**」。2 到 4 條,每條是「小標 + 一句說明」,不是長段落
7. **實用資訊行** —— 營業、費用、車程、導覽、訂位、預約、下車點、接續動線
8. **狀態徽章** —— 已預定/已購票/現場代排,含時間與人數
9. **「務必」**(只在有硬性限制或矛盾時出現)—— 比「建議」高一級的欄位,放不能違反的事與查到的矛盾:「務必 17:00 閉館 —— 行程寫 17:40 才前往下一站,實際 17:00 就得離館」。用一個專屬標籤而不是混進建議裡,才不會被讀過去
10. **建議** —— 停留多久 + 排程判斷。這是整頁的結論,不要省

視項目性質再加:

- **最佳時段** —— 攝影或景觀類項目要獨立列出來,不要只藏在推薦理由裡:「清晨人少,是拍石庫門立面最好的時段」、「傍晚夕陽轉夜景」。使用者可能會為了這一句調整當天順序
- **價格的變動與不確定性** —— 「成人門票 RMB 60(2026 年花卉節期間曾調降為 25,請當日確認)」

### 把單項頁做成可重複的元件,不要每頁手刻

38 頁如果每頁的樣式各寫一次,改一個間距要改 38 次。ref 的做法是一組固定的 class,每頁只填內容:

| 元件 | 用途 |
|---|---|
| `.card` + `.card-head` / `.card-strip` / `.card-media` / `.card-sec` / `.card-foot` | 單項頁的骨架:標題區、類型色帶、圖片區、內容小節(一頁通常 2 個)、頁腳資訊 |
| `.irow` + `.ik` + `.iv` | 實用資訊列:一列一個「鍵 + 值」(營業 / 費用 / 車程),整份文件對齊一致 |
| `.sched` + `.tm` / `.ev` / `.note` | 日扉頁時間軸:時刻欄、事件欄、備註 |
| `.today` | 今日重點框 |
| `.tip` | 提示框(每一兩頁一個) |
| `.legend` | 圖例 |
| `.fill` | **紙本專用的手寫填空線**:`display:inline-block; min-width:34mm; border-bottom:.2mm solid` |

**紙本要留可以手寫的空位。** 保險專線、信用卡掛失、緊急聯絡人這些使用者還沒提供的欄位,在螢幕版是「(投保後填入)」,在**紙本要給一條實際的底線讓他當場用筆填**。這是紙本才有的優勢,不要只把螢幕版的括號註記照搬。

**狀態用顏色編碼,而且要與圖例一致:**

- **紅色系** —— 不能違反的事:硬時間、務必、逾時不候
- **綠色系** —— 已完成:已預定、已購票、旅行社已完成
- **類型色** —— 景點色與餐飲色分開,翻頁時一眼認出這一頁是吃的還是看的

顏色只是輔助,**每個顏色都要有文字標籤** —— 列印成黑白、或色弱的讀者只看顏色會全部失效。

### 圖片:列印版會裁切,挑圖必須先算長寬比

規則與詳細版相同(見「加入使用者提供的圖片」一節),但有一個**只有列印版才有的陷阱**。

詳細版的圖是 `height:auto`,**不裁切**。列印版為了讓「一項一頁」的版面整齊,圖通常放在固定高度的框裡配 `object-fit:cover` —— 那會**裁切**。而固定高度的框往往比圖本身寬扁得多,裁掉的量比想像大:

以 B5 內容寬 150mm、框高 44mm(3.41:1)為例:

| 圖的比例 | 常見的圖 | 裁掉的高度 |
|---|---|---|
| 0.75:1(直幅) | 瀑布、塔、人像 | **約 78%** —— 主體整個消失 |
| 1.00:1(正方) | 食物俯拍 | 約 71% |
| 1.33:1(4:3) | 一般相機橫幅 | 約 61% |
| 1.50:1(3:2) | 單眼橫幅 | 約 56% |
| 2.09:1 | 全景 | 約 39% |

**連全景都裁掉四成。所以不能只有一種版位。**

但**長寬比只是一半的答案。真正決定的是「主體在畫面裡怎麼分布」** —— 裁掉多少不重要,裁掉的是不是主體才重要。實測證據:一張 1.33:1 的山路照塞進 3.41:1 的框、裁掉 61%,結果非常好看,因為那條路是橫向帶狀、剛好落在垂直中段,裁掉的是上方的天空與下方的前景。同一個框放一張直幅瀑布就毀了。

| 主體分布 | 該用什麼版位 | 常見的圖 |
|---|---|---|
| **橫向帶狀、落在垂直中段** | **寬扁版位 + 正中裁切最理想**,裁掉 60% 也無妨 | 道路、小徑、稜線、地平線、花田、河岸 |
| **縱向延伸** | 寬扁版位會毀掉主體 → 高幅或圖文並排 | 瀑布、塔、樹、站姿人像、樓梯 |
| **畫面中央的單一物件** | 接近原比例的版位,或 `contain` | 食物、單朵花、雕塑、招牌 |
| **主體明顯偏上或偏下** | 任何版位 + `object-position` 指定重心 | 雲海在上半、花田在下半 |

**你在步驟 3 已經把每一張圖打開看過了 —— 那份資訊就是用來選版位的。** 不要看完只用來寫圖說,然後把九張圖全部塞進同一個框。

版位尺寸(依圖的比例與主體分布挑一個):

| 版位 | 尺寸(B5) | 比例 | 適合 |
|---|---|---|---|
| 全景帶 | 150 × 50mm | 3:1 | 2.6:1 以上 |
| 標準 | 150 × 75mm | 2:1 | 1.8–2.6:1 |
| 高幅 | 150 × 100mm | 1.5:1 | 1.3–1.8:1(4:3、3:2 這些最常見的) |
| **圖文並排** | 70 × 95mm | 0.74:1 | **直幅與正方** —— 圖放一側、文字放另一側,不要硬拉成橫幅 |

另外三條:

- **選版位要同時看兩件事**:實際長寬比(`pics/cc/_licences.json` 已記 `w`/`h`,使用者提供的圖要先量)與**主體分布**(你打開看過就知道)。只看比例不看主體,會把橫向帶狀的好素材誤判成不能用寬扁版位。
- **裁切重心用 `object-position` 指定。** 主體不在正中間的(花田在下半部、天空佔上半部)要寫 `object-position:center 70%` 這類。**預設的正中裁切只有在主體剛好居中時才對** —— 而那是運氣,不是設計。每一張都要判斷一次,判斷完覺得正中就對的,也要明確寫出來或至少心裡有數,不要靠沒設定。
- **構圖不能裁的就不要裁** —— 瀑布、單朵特寫、建築全貌這種,改用圖文並排版位,或 `object-fit:contain` 加底色。**寧可留白,不要裁成一條橫帶。**

還有一個現實情況:**同一批圖在兩份文件的適用性不同。** 詳細版能用的直幅圖,列印版可能只能改成並排、或乾脆不用。這一點要在挑圖時就跟使用者講,不要讓他以為兩份會長一樣。

列印版一律用 **base64 內嵌** —— 紙本流程常常是「存成 PDF 再寄出去」,相對路徑會在轉 PDF 時破圖。

### 維護

列印版做完後詳細版仍然保留,兩者用途不同。之後內容有變動,**先改詳細版,確認後再同步列印版**,並記得重編頁碼與更新版本號。
